1Purpose & scope

This guide proposes how Consumer Direct will ingest state unclaimed-property data in production: a durable, governed S3 data lake that automatically fetches each state's source file and feeds Snowflake, where the data is transformed, diffed, and matched against member identities.

The design is a deliberate ELT split. S3 is the durable system of record for the raw source files — every refresh lands as an immutable, dated snapshot, giving us the provenance/audit trail compliance requires. Snowflake (via dbt) is where all transformation, the new/claimed snapshot diff, and serving happen — the warehouse Consumer Direct already operates. Acquisition is fully automatic (a scheduled conditional fetch — see §5.1), so no manual download or upload is ever required for a supported state.

Design principle. S3 holds immutable, dated snapshots per source. We never overwrite — every refresh is a new partition. This makes the snapshot-diff (new vs. claimed) trivial and gives us the auditable substantiation trail compliance requires (matching algorithm, accuracy, timestamps).

AWS building blocks: S3 (lake) · Fargate (fetch + unzip) · Step Functions + EventBridge (orchestration/schedule) · Snowpipe + external stage (load) · dbt (transform + snapshot diff) · KMS (encryption) · Secrets Manager (SFTP/API creds).

Recommended pattern: ELT — keep transforms & diffs in Snowflake. S3 is used only to land raw (fetch + unzip). All real work — column mapping to the canonical schema, name normalization, decedent suppression, NAUPA decoding, and the new/claimed snapshot diff — runs in Snowflake via dbt, the warehouse Consumer Direct already operates. This means one transform engine (SQL, version-controlled, tested) instead of a second standalone transform runtime; dbt's built-in snapshot is purpose-built for the new/claimed change-tracking; and Snowflake scales the 38M-row joins where the matcher already lives. The only processing that cannot move into Snowflake is unzip — COPY reads gzip/bzip2 but not .zip archives, and CA ships .zip. So the S3-side job is fetch + unzip, nothing more. (Revisit pushing a cheap Parquet/prune step back to S3 only if volume grows to many states × frequent refreshes.)

4S3 bucket & prefix layout

One bucket per environment (e.g. cd-unclaimed-property-prod), zoned by prefix. Every object is partitioned by source, state, and snapshot_date so snapshots are immutable and prunable.

Under the ELT pattern, S3 holds only raw data (the archive and the unzipped CSVs that Snowflake loads). The canonical PROPERTY table and the new/claimed/active status are tables in Snowflake, not S3 zones.

raw/  immutable

raw/{source}/{state}/{snapshot_date}/

Exact bytes as received (the .zip) + a _manifest.json. Object-versioned. Never edited.

raw/…/csv/  load source

raw/{source}/{state}/{snapshot_date}/csv/

Unzipped .csv.gz — what Snowpipe / COPY reads. Re-derivable from the zip.

quarantine/

quarantine/{state}/{snapshot_date}/

Files that failed validation, with the failure report. Manual review.

logs/

logs/access/ · logs/runs/

S3 access logs + per-run metadata for the audit trail.

Snowflake curated

raw.property_landing → stg_property → PROPERTY · property_snapshot

Canonical rows + per-property status live here (dbt), beside the matcher.

Example object keys (S3 holds raw only)
raw/ca_sco/CA/2026-06-01/04_From_500_To_Beyond.zip
raw/ca_sco/CA/2026-06-01/_manifest.json
raw/ca_sco/CA/2026-06-01/csv/04_From_500_To_Beyond.csv.gz   ← Snowflake loads this
# canonical PROPERTY + new/claimed status: tables in Snowflake (dbt), not S3
Partitioning by snapshot_date (not just “latest”) preserves the history the compliance substantiation file needs and lets dbt detect the new/claimed change cheaply. Lifecycle rules transition the .zip in raw/ to Glacier after 90 days; the unzipped csv/ expires after a few days (re-derivable from the zip, and already loaded into Snowflake).

5Ingestion pipeline stages

5.1 — Acquire (land raw)

How “automatic” actually works: the State Controller does not push data or notify us, so ingestion is a scheduled pull. An EventBridge schedule (e.g. weekly) starts a Fargate task that issues a conditional GET against the CA bulk URL — it compares the source ETag/Last-Modified to the last landed snapshot and only downloads when the file has changed, streaming it into a fresh dated raw/ snapshot and writing a manifest (etag, byte size, fetched-at). Re-runs are idempotent (it skips an already-landed snapshot). Only California publishes an open, commercial-use bulk feed, so it is the only state polled this way; TX (PI-license file) and NY (OSC SFTP) arrive via DataSync/approved drop — see §10.

Why Fargate, not Lambda: the CA tiers are ~1 GB+ zips; Lambda's 15-min timeout and ephemeral-storage limits make it the wrong tool. A Fargate task (or AWS Batch) has no wall-clock limit and streams a multipart upload to S3.

Acquire — CA SCO bulk → S3 (conditional GET, idempotent)
import boto3, hashlib, json, datetime as dt, httpx

S3 = boto3.client("s3")
BUCKET = "cd-unclaimed-property-prod"
SNAPSHOT = dt.date.today().isoformat()
TIERS = ["04_From_500_To_Beyond.zip", "03_From_100_To_Below_500.zip",
         "02_From_10_To_Below_100.zip", "01_From_0_To_Below_10.zip"]

def last_etag(tier: str) -> str | None:
    # ETag of the most recently landed copy of this tier, if any.
    r = S3.list_objects_v2(Bucket=BUCKET, Prefix=f"raw/ca_sco/CA/", Delimiter="/")
    # (in practice: read it from the latest snapshot's _manifest.json)
    return None

def land_ca_tier(tier: str, prior_etag: str | None):
    url = f"https://claimit.ca.gov/upd-property-records/{tier}"
    # Conditional GET: only download if CA changed the file since last run.
    head = httpx.head(url, follow_redirects=True, timeout=60)
    etag = head.headers.get("etag")
    if etag and etag == prior_etag:
        return None                      # unchanged → nothing to ingest
    key = f"raw/ca_sco/CA/{SNAPSHOT}/{tier}"
    with httpx.stream("GET", url, follow_redirects=True, timeout=600) as r:
        r.raise_for_status()
        S3.upload_fileobj(r.iter_bytes(1 << 20), BUCKET, key,   # multipart under the hood
                          ExtraArgs={"ServerSideEncryption": "aws:kms"})
    return {"key": key, "etag": etag}

landed = [x for t in TIERS if (x := land_ca_tier(t, last_etag(t)))]
if landed:   # write a manifest only when something actually changed
    S3.put_object(Bucket=BUCKET, Key=f"raw/ca_sco/CA/{SNAPSHOT}/_manifest.json",
                  Body=json.dumps({"source":"ca_sco","state":"CA","snapshot_date":SNAPSHOT,
                                   "files":landed,"fetched_at":dt.datetime.utcnow().isoformat()+"Z"}),
                  ServerSideEncryption="aws:kms")

5.2 — Validate

Before transforming, gate the raw drop: confirm expected files are present, the CSV header matches a known shape, the row count is within an expected band of the prior snapshot (a sudden 90% drop usually means a truncated download, not 90% claimed), and the checksum is stable. Failures move the snapshot to quarantine/ and page the on-call — they are never loaded into Snowflake.

5.3 — Unzip (the only S3-side processing)

Snowflake's COPY reads gzip/bzip2/zstd but not .zip archives, and CA ships .zip files containing CSVs. So a small Fargate step decompresses each archive and writes the member CSVs back to S3 (re-compressed as .csv.gz, which COPY reads natively). That is the only data processing outside Snowflake — no column mapping, no normalization, no diff happens here.

Unzip — raw .zip → .csv.gz in S3 (no transformation)
# Fargate task: stream each CSV out of the zip, gzip it, put back to S3
import zipfile, gzip, io, boto3
S3 = boto3.client("s3")
zf = zipfile.ZipFile(local_zip)
for name in (n for n in zf.namelist() if n.lower().endswith(".csv")):
    buf = io.BytesIO()
    with zf.open(name) as src, gzip.GzipFile(fileobj=buf, mode="wb") as gz:
        for chunk in iter(lambda: src.read(1 << 20), b""):
            gz.write(chunk)
    buf.seek(0)
    S3.upload_fileobj(buf, BUCKET,
        f"raw/ca_sco/CA/{SNAPSHOT}/csv/{name}.gz",
        ExtraArgs={"ServerSideEncryption": "aws:kms"})

5.4 — Transform in Snowflake (dbt)

Everything else is SQL. After the raw CSVs land in a Snowflake landing table (§9), a dbt staging model maps each source's columns to the canonical schema (§6), normalizes owner names for matching, parses amounts, and drops decedent/estate records (v1 compliance) — one tested, version-controlled model per source:

models/staging/stg_property_ca.sql — runs in Snowflake
{{ config(materialized='incremental', unique_key=['holder_id','snapshot_date']) }}
SELECT
    PROPERTY_ID                                          AS holder_id,
    HOLDER_NAME                                          AS holder_name,
    OWNER_NAME                                           AS owner_name,
    UPPER(TRIM(REGEXP_REPLACE(OWNER_NAME,'\\s+',' ')))   AS owner_name_normalized,
    OWNER_STREET_1                                       AS last_known_address,
    OWNER_CITY                                           AS last_known_city,
    OWNER_STATE                                          AS last_known_state,
    OWNER_ZIP                                            AS last_known_zip,
    TRY_TO_DECIMAL(CASH_REPORTED, 14, 2)                 AS amount_min,
    TRY_TO_DECIMAL(CURRENT_CASH_BALANCE, 14, 2)          AS amount_max,
    PROPERTY_TYPE                                        AS property_type,
    'CA'                                                 AS state,
    metadata$filename                                    AS source_file,
    TO_DATE(REGEXP_SUBSTR(metadata$filename,'\\d{4}-\\d{2}-\\d{2}')) AS snapshot_date
FROM {{ source('raw','property_landing') }}
WHERE NOT REGEXP_LIKE(UPPER(OWNER_NAME), '.*(ESTATE|DECEASED|EST OF).*')

Header names vary by state and are undocumented; maintain a per-source header-alias map (one staging model per source) so a column rename in a future file degrades to NULL rather than breaking the load. The diff (§7) and serving (§9) are likewise pure dbt/Snowflake — each model reads only the new snapshot_date, so reprocessing one state never touches another.

7Snapshot diff (new / claimed)

When a state republishes its file, a property that was claimed drops out and newly reported money appears. This is exactly change-data-capture across dated snapshots — so use dbt's built-in snapshot (in Snowflake) rather than a hand-rolled S3 job. dbt tracks each holder_id over time; a record that stops appearing is claimed, a first-time one is new, the rest are active. The UI buckets new/active as claimable and claimed as history.

snapshots/property_snapshot.sql — dbt snapshot (Snowflake)
{% snapshot property_snapshot %}
{{ config(target_schema='snapshots', unique_key='holder_id',
          strategy='check', check_cols=['snapshot_date']) }}
  SELECT holder_id, owner_name_normalized, amount_max, snapshot_date
  FROM {{ ref('stg_property_ca') }}
{% endsnapshot %}

-- derive status from the snapshot's validity window (dbt_valid_to IS NULL = current)
SELECT holder_id,
       CASE WHEN dbt_valid_from = (SELECT MAX(dbt_valid_from) FROM property_snapshot s2
                                   WHERE s2.holder_id = s.holder_id)
                 AND dbt_valid_to IS NULL THEN 'active'
            WHEN dbt_valid_to IS NULL THEN 'active'
            ELSE 'claimed' END AS status
FROM property_snapshot s;

Underlying logic is a FULL OUTER JOIN on holder_id between the current and prior snapshot; dbt snapshots give you that plus the history table, tests, and lineage for free. No S3 diffs/ zone is needed — the status lives in Snowflake next to PROPERTY.

8Orchestration & scheduling

  • EventBridge schedule kicks off a Step Functions state machine per source (CA monthly; others on their cadence).
  • State machine = Acquire (conditional GET) → Validate → (branch on pass/quarantine) → Unzip → Snowpipe/COPY raw → dbt build (staging → canonical → snapshot diff → tests) → notify.
  • Each step is idempotent and keyed by {source, state, snapshot_date}; a retry re-uses the already-landed raw object rather than re-downloading.
  • dbt (Cloud or in a Fargate task) builds SOURCE_REGISTRY, PROPERTY, and CLAIM_CASE and runs tests; failures block promotion to the serving schema.

9Loading into Snowflake

Point an external stage at the raw/…/csv/ prefix and COPY the unzipped CSVs into a Snowflake landing table (raw columns as-is). dbt (§5.4, §7) does everything after. The landing table keeps the source filename so snapshot_date is recoverable.

Snowflake — external stage + COPY raw CSV → landing table
CREATE STORAGE INTEGRATION ucp_s3
  TYPE=EXTERNAL_STAGE STORAGE_PROVIDER=S3 ENABLED=TRUE
  STORAGE_AWS_ROLE_ARN='arn:aws:iam::<acct>:role/snowflake-ucp'
  STORAGE_ALLOWED_LOCATIONS=('s3://cd-unclaimed-property-prod/raw/');

CREATE STAGE ucp_raw
  URL='s3://cd-unclaimed-property-prod/raw/'
  STORAGE_INTEGRATION=ucp_s3
  FILE_FORMAT=(TYPE=CSV SKIP_HEADER=1 FIELD_OPTIONALLY_ENCLOSED_BY='"' COMPRESSION=GZIP);

-- Load raw rows verbatim (the .csv.gz from the unzip step). dbt maps them next.
COPY INTO raw.property_landing
  FROM @ucp_raw
  PATTERN='.*/csv/.*[.]csv[.]gz'
  INCLUDE_METADATA=(file_name=METADATA$FILENAME);   -- snapshot_date parsed in dbt

A scheduled COPY (gated by the Step Functions success signal) suits a monthly bulk drop better than always-on Snowpipe — cheaper and deterministic. Snowpipe (S3 event → SQS) is the option if a source starts delivering frequent incremental files. Either way, the load is raw-only; transforms stay in dbt.

10Security & compliance

Data protection

  • Encryption: SSE-KMS at rest (a dedicated CMK), TLS 1.2+ in transit. The bucket blocks all public access and is reached only via VPC gateway endpoints.
  • IAM least privilege: the acquire/unzip role PutObjects the zip and csv/ under raw/; Snowflake's storage-integration role reads raw/ only. No human has standing write access to raw/, and Snowflake never writes back to S3.
  • PII: owner names + addresses are personal data — access-logged, never replicated to non-prod unmasked, covered by the GLBA/Reg P privacy notice for the UP-matching purpose.
  • Provenance / substantiation: immutable dated snapshots + manifests give the timestamped accuracy trail the Credit Karma/Pfizer-style defense requires.

Per-state ingestion legality load-bearing

We only ingest where it is clearly permitted; everywhere else we deep-link the member to the state's own portal (no server-side scraping).

The acquisition layer must refuse to fetch any source not on the allow-list, even if a URL exists — the allow-list is code, not config, and changing it requires legal sign-off.

11Data quality & idempotency

  • Idempotent by key. Re-running a snapshot is a no-op (head-object skip on acquire; partition overwrite on transform). Safe to retry any stage.
  • Manifests + checksums tie every curated partition back to the exact raw bytes it came from.
  • dbt tests: not-null on holder_id/owner_name, accepted range on amounts, row-count delta vs. prior snapshot within tolerance, no duplicate (holder_id, owner_name_normalized) within a snapshot.
  • Quarantine over silent acceptance — a bad file never reaches members.

12Cost & scale

  • CA is ~12 GB / ~38M rows per snapshot raw; gzip keeps the S3 copy small, and Snowflake stores the canonical table compressed (columnar) — S3 storage is pennies/GB-month either way.
  • S3 storage is pennies/GB-month; the real levers are transform compute (one Fargate task, minutes) and Snowflake credits on load/model — favor a scheduled monthly COPY over always-on Snowpipe for bulk drops.
  • Partition pruning (state, snapshot_date) keeps query and reprocessing cost proportional to the one snapshot that changed.
